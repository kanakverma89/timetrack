# Decisions

Conservative defaults chosen where `spec.md` leaves room. Each is revisitable.

| ID | Decision | Rationale |
| --- | --- | --- |
| D-1 | **Project root is the current directory**, not a nested `timesheet-app/`. | Directory is already the project; avoids a redundant level. |
| D-2 | **Auth = local email/password**, Argon2id, server-side sessions in an HttpOnly cookie. OIDC is the production-preferred path and can replace `security/sessions.py` later. | Self-contained prototype per spec §11.1; no employer IdP coupling. `.env.example` uses `SESSION_TTL_HOURS` instead of access/refresh token settings because there are no bearer tokens. |
| D-3 | Session token digest is stored with HMAC-SHA256 keyed by `SESSION_SECRET`. | A DB leak alone does not yield usable session tokens. |
| D-4 | CSRF guard = required `X-Requested-With: timetrack` header + `Origin` allow-list check on unsafe methods. | Simple, stateless, works with SameSite=Lax; no token round-trip. |
| D-5 | **Login throttling is in-memory** (5 failures / 15 min per address+email). | Adequate for one process. Documented limitation; use Redis or a DB table before scaling out. |
| D-6 | **`GET /timesheets/weeks/{date}` is read-only.** If no week row exists it returns an empty `DRAFT` representation with `id: null`. The row is created on the first write (Phase 3). | Repeated GETs can never create duplicates and GET stays side-effect free (spec §8.4 allows either). |
| D-7 | The week endpoint **normalises any date** to its week start and returns the normalised dates. Years outside 1970–2100 are rejected with 422. | Robust navigation and deep links; avoids date overflow. |
| D-8 | `GET /meta` returns business timezone, week start day, server "today", current week start and entry limits. | Business dates come from the server, not the browser clock. |
| D-9 | **No UI component library**; small accessible custom components with CSS tokens. | Few components in this milestone; native elements give accessibility for free; avoids a heavy dependency. Revisit for the combobox in Phase 3. |
| D-10 | **TanStack Query** for server state, no global store. | Retry, caching and de-duplication are needed; shared client state is not. |
| D-11 | Entry "status" equals the parent week's status; `draft_count` = number of entries while the week is `DRAFT` or `REJECTED` (editable), else 0. | Entries have no status column in spec §7.8. |
| D-12 | Capped/non-capped comes only from `earning_codes.classification`. Seed meaning of "capped" is illustrative and policy-neutral. | Spec §3.4, §7.6. |
| D-13 | Hours are `NUMERIC(5,2)` in the DB, `Decimal` in Python, **strings** in JSON, and never floats. DB check: `0 < hours <= 24`; app-level per-entry maximum is `MAX_HOURS_PER_ENTRY` (default 24). | Spec §3.4, §8.1. |
| D-14 | Reference-data routes call repositories directly (no pass-through service). | Avoids empty abstraction; add a service when rules appear. |
| D-15 | Sync SQLAlchemy 2.x with `psycopg` 3; FastAPI sync path operations run in the thread pool. | Simpler transactions/locking (`SELECT … FOR UPDATE` in Phase 5); load is modest. |
| D-16 | Seeded users share one password supplied via `SEED_PASSWORD`; the seed script refuses to run without it (min 12 chars) and in `production`. | No credentials in source. |
| D-17 | Cross-table "work_date inside the week" is enforced in the service layer (Phase 3), not by a DB trigger. Other integrity rules (owner match, task⇄project) use composite FKs. | Triggers add operational surface; revisit during hardening. |
| D-18 | English (`en-US`) formatting and Monday-first display only. | i18n is out of scope. |
| D-19 | Light theme only (WCAG-oriented contrast, visible focus). | Dark mode is not required for the milestone. |
| D-20 | Phase 2 had no "Add entry" button or row actions. **Superseded by Phase 3**, which adds them (Edit/Delete/Add entry appear only while the week is editable). | Controls that do nothing would have been placeholders. |
| D-21 | A `403`/`404` policy: unknown or foreign resources return `404 NOT_FOUND`; missing role returns `403 FORBIDDEN`. | Avoids resource enumeration (spec §11.2). Applies from Phase 3. |
| D-22 | **ESLint is pinned to v9** (`eslint`, `@eslint/js`). | `eslint-plugin-jsx-a11y@6` declares peer support only up to ESLint 9; v10 would need `--legacy-peer-deps`. Revisit when the plugin supports v10. |
| D-23 | The query client retries transient failures (network, 5xx) twice and never retries 4xx. A 401 on any data request clears the cached session and returns the user to sign-in with a notice. | Spec §10.1 (error + retry, expired session). |
| D-24 | E2E runs against a disposable `timetrack_e2e` database recreated and seeded on every run by `backend/scripts/prepare_db.py`; the login throttle is raised for that run only. Phase 2 specs are read-only so they can run in parallel across browsers; mutating specs (Phase 3+) must create their own data or run serially. | Deterministic data, no cleanup logic. |
| D-25 | Tab-order assertions are skipped on WebKit/macOS (Safari-family engines do not Tab onto buttons by default); keyboard activation is still tested on all engines. | Engine behaviour, not an app defect (native `<button>`s are used). |
| D-26 | CI runs the backend on Python 3.12 (declared minimum) and 3.14, and the frontend on Node 22, 24 and 26. **The Node minimum is 22.22**, not 20: running CI on Node 20 showed `vitest 5` and `jsdom 30` do not start there (Vite alone would). `engines` + `engine-strict` make an unsupported Node fail at install with a clear message. Node 20 is also past end-of-life. | Found by the version matrix; downgrading test tools to keep an EOL runtime was rejected. |
| D-27 | **Task is required only when the chosen project has active tasks.** On edit the rule applies only if the project or task actually changes, so editing the hours of an older entry is never blocked by tasks added later. Unchanged references to since-retired projects/codes/tasks stay allowed on edit; new entries need active ones. | Spec §3.6 and rule 7/8; found via a test that mirrored the edit form re-sending unchanged fields. |
| D-28 | `PATCH` cannot move an entry to a date in a different week (422 with an explanation); delete and re-add instead. | Moving between weeks needs two week locks and two editability checks; deferred rather than risking deadlocks or silent re-parenting. |
| D-29 | Entry changes are audited in an append-only `time_entry_events` table (CREATED/UPDATED/DELETED, actor, ids/date/hours and which fields changed). **Free-text descriptions are never copied** (only a `description_changed` flag). `time_entry_id` is not a foreign key so history survives deletion. No read API/UI yet. | Spec §4.1/§11.4 "auditable" without duplicating sensitive text. |
| D-30 | The week row is created lazily on the first write using `INSERT … ON CONFLICT DO NOTHING` followed by `SELECT … FOR UPDATE`; every entry write locks its week first. Concurrent first writes yield exactly one week; concurrent writers are serialised. Failed validation creates no week. | Spec §7.7/§8.4; the same lock will guard submission in Phase 5. |
| D-31 | A `REJECTED` week stays editable and **keeps its status and reason** until resubmission (Phase 5). | Reason must remain visible (spec §3.8, rule 12). |
| D-32 | `PATCH` accepts an optional `version`; a mismatch returns 409 `STALE_ENTRY`. The UI always sends it. `version` increments only when something actually changed. | Optimistic concurrency (spec §7.8). |
| D-33 | Write payloads reject unknown fields (`extra="forbid"`), so `employee_id`, week ids or status can never be client-supplied. Foreign or unknown entry ids both return 404 `NOT_FOUND`. | Spec §11.2; implements D-21. |
| D-34 | Mutating E2E tests each own one far-future week derived from a registered test key and the browser project, so tests never share data even in parallel; each test empties its week first (safe on retries). | D-24 covered read-only tests only. |
| D-35 | Modals (`components/Modal.tsx`) are hand-rolled: focus trap, Escape, `inert` page, focus restore. The opener is the focused control, else the last clicked button (Safari/WebKit focus `<main>` or `<body>` on click). Focus is restored only if it was lost, so stacked modals closing together do not fight. | Found through E2E on WebKit and React StrictMode; unit tests alone did not expose it. |
| D-36 | The Day/Week toggle was withheld until Week mode existed. **Superseded by Phase 4** (D-38 to D-42). | Same reasoning as D-20. |
| D-37 | The project combobox loads all active projects (server caps at 200) and filters client-side. | Fine for the current data volume; switch to server-side `?search=` if projects grow large. |
| D-38 | **Batch contract (`POST /time-entries/batch`)**: 1–31 items, all dates in **one week** (the first valid item defines it), each date **at most once**, every item fully validated before anything is written, then all rows and audit events inserted in a single transaction (all or nothing). Field errors are keyed `entries.<index>.<field>`. A batch only ever *adds* entries; it never replaces or merges with existing ones. | Spec §3.7, §8.5, rule 14. Duplicate dates are refused because Week mode has one input per day, so a repeat can only be a client bug. |
| D-39 | In Week mode a day that is blank, `0`, or unchecked records nothing (hours are `≥ 0` in the UI, `> 0` in the database/API). At least one day with positive hours is required. Saturday and Sunday start unchecked, judged by the date's actual weekday (not by the configured week start). | Spec §3.7. |
| D-40 | Day and Week mode keep **separate state** in the panel; project, task, earning code and description are shared. Switching modes changes nothing the user typed; toggling alone is not "unsaved work". The toggle is shown only when adding (editing is always one entry). | Spec §3.7 "switching modes does not silently lose data". |
| D-41 | The batch response returns the created entries **plus the recomputed week summary and daily totals**; the UI still refetches the week so there is one source of truth. | Spec §8.5. |
| D-42 | The grid shows "Already logged: N h" per day from the week's daily totals. | Prevents accidental double entry now that existing records are never replaced. |
| D-43 | **Submission is one transaction under a row lock.** `POST /timesheets/weeks/{date}/submit` locks the week row, checks the state (DRAFT/REJECTED only, else 409 `INVALID_TRANSITION`), re-validates, then writes status + `submitted_at`, the append-only `approval_events` row, the notification outbox row and the idempotency key together. Any failure leaves nothing behind. Concurrent submits serialise on the lock: exactly one wins, the rest get 409 (or 200 if they carry the same key). | Spec §3.8, §8.6, rule 13, 17. |
| D-44 | **`Idempotency-Key`** (optional header, 8–100 of `[A-Za-z0-9_-]`) is stored in `idempotency_keys`, unique per `(user, scope, key)` and bound to the week it first acted on. A retry with the same key and week returns the current week with 200 and does nothing; the same key for a different week is 422. Keys are not expired yet (retention is a Phase 7 item). The UI generates one key per opened dialog, so retries of one action share it and a new dialog gets a new one. | Spec §3.8 "where practical"; turns a lost response or double click into success instead of a confusing conflict. |
| D-45 | At submission the stored entries are **re-checked against the current limits** (hours, description, date inside the week). Inactive projects/codes/tasks do **not** block submission: they were valid when the entry was written (spec rule 7, 16). | Limits can change after entries are written. |
| D-46 | **Weekly policy is optional configuration:** `MAX_HOURS_PER_DAY` and `MAX_HOURS_PER_WEEK`, both **unset by default** (no rule is invented). They are checked only at submission, with errors keyed `day.<date>` and `week`. | Spec §3.8 "any configured weekly policy", rule 18. |
| D-47 | Resubmitting a REJECTED week **clears** `reviewed_at`, `reviewed_by` and `review_comment` on the live row; the earlier decision stays in `approval_events`. | The row describes the current submission; history is not lost. |
| D-48 | **Notifications:** business code only writes an outbox row (`TIMESHEET_SUBMITTED`, ids and totals, never descriptions or comments). After the response, a background task claims pending rows with `FOR UPDATE SKIP LOCKED` and hands them to a `NotificationPort` (development adapter: structured log line). Failures record `attempt_count` and a short error, retry up to `NOTIFICATION_MAX_ATTEMPTS`, then park the row as `FAILED`; they never affect the API response. Rows stuck in `PROCESSING` by a crash are not recovered yet. | Spec §6.1, §7.10. |
| D-49 | Confirm actions (Save, Delete, Submit) are guarded by a **synchronous in-flight flag**, not only a disabled button, because two clicks can land before React re-renders. When an action fails, focus moves to the error message (a disabled, focused button otherwise drops focus to `<body>` and Escape stops working). | Found by Playwright (double-click sent two requests) and an axe/keyboard test. |
| D-50 | Until manager decisions exist (Phase 6), E2E tests reach REJECTED/APPROVED weeks with `backend/scripts/e2e_state.py`, which edits the disposable E2E database only (refuses any name not ending `_test`/`_e2e`). The E2E server runs with `MAX_HOURS_PER_DAY=16` and `MAX_HOURS_PER_WEEK=60`. Tests that submit get a fresh week per retry, because a submitted week cannot be reset. | Test set-up, not an application feature. |

## Open questions (no answer needed to proceed)

- What does "capped" mean for the business (e.g. a weekly cap on a class of hours)? Currently only
  a classification; no cap is enforced.
- Should past/future weeks be restricted? Not restricted; no policy was given.
- Is withdrawal of a submitted week wanted? Not designed; `WITHDRAWN` exists in the audit enum only
  as an option.
